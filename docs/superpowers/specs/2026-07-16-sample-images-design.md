# Unified sample-image system — design

**Date:** 2026-07-16
**Branch:** kg/e2e-images
**Goals:** (1) demo and test images live in one part of the filesystem, each with the
required item-name metadata; (2) a failing e2e test is diagnosable from the image in its
screenshot.

## Problem

Sample images are scattered: demo/walkthrough images in `public/onboarding/`, e2e upload
fixtures in `e2e/fixtures/photos/` (CC0 jpegs + `IMG_0428.jpeg`), and a third set in
`e2e/fixtures/demo-images/` (40 webps, now redundant — `photo-serving.ts` searches it only
as a fallback behind `public/onboarding`). Every spec uploads the same 1–3 anonymous jpegs,
so a failure screenshot says nothing about which test created which item.

## Design

### 1. Layout

```
public/sample-images/
  demo/                  # moved from public/onboarding/ (committed, shipped to prod)
  test/
    base/                # curated photos, committed — one per spec, named for the spec
    labeled/             # generated by sharp, gitignored — never committed or deployed
```

- `public/onboarding/` moves to `public/sample-images/demo/`. Mechanical rename in
  `sampleData.ts` (imageSrc URLs), `photo-serving.ts` (search path),
  `dev-sample-bootstrap.ts`, `ATTRIBUTION.md`, and their tests.
- `e2e/fixtures/photos/`, `e2e/fixtures/demo-images/`, and `scripts/fetch-demo-images.mjs`
  are deleted. `photo-serving.ts` drops the demo-images search path;
  `photo-serving.test.ts` points its placeholder-read case at a demo image.
- `public/sample-images/test/labeled/` is gitignored; only committed files reach a Vercel
  build, so test images never ship.

### 2. Test image set

- **One base photo per spec file** that uploads a photo (~19: every spec referencing
  `e2e/fixtures/photos/`, including `a11y.spec.ts`), named for the spec:
  `sort-images.webp`, `results-rerank.webp`, …
- **Aesthetic contract:** single household object, red/orange/yellow dominant, modern
  editorial ("Dwell") styling — deliberately distinct from the cozy demo set, so a glance
  at a screenshot tells demo data from test data.
- **Sourcing:** the owner generates the photos from prompts supplied in
  `docs/test-image-prompts.md` (shared style block + one object prompt per spec) and drops
  them in `base/`.

### 3. Metadata

`public/sample-images/test/manifest.ts` mirrors the demo set's `SAMPLE_ITEMS` shape — one
entry per spec: `{ spec, itemName, file }`, with `itemName` required. Specs import their
entry instead of hardcoding paths. The demo manifest (`sampleData.ts`) is unchanged apart
from the moved `imageSrc` prefix.

### 4. Label overlay (diagnosability)

`scripts/label-test-images.mjs` composites the spec name onto each base photo using sharp
(already a dependency) and writes to `labeled/`. Playwright `globalSetup` runs it (added if
absent), so labels regenerate every run — a renamed test can never carry a stale label.
~19 images, sub-second.

### 5. Spec migration

- Each spec's `PHOTO_FIXTURE` points at its own `labeled/<spec>.webp`.
- `route.fulfill` image stubs switch `contentType` to `"image/webp"`.
- Any assertion on an uploaded filename/extension (`.jpg`) is updated alongside.
- **Exception:** `e2e/screenshots/capture.ts` is the docs/PR screenshot harness, not a
  test — it uses a **demo** image so published screenshots show the app looking real.

## Alternatives considered

- **Labeled color cards (no photos):** maximum diagnosability, zero binaries, but the app
  never looks real in test screenshots. Rejected by owner in favor of hybrid.
- **Curated photos without overlay:** looks real, but diagnosis needs a filename↔test
  lookup. Rejected — the label is the point.
- **Keep `public/onboarding/` in place, add a sibling test dir:** fewer renames, but fails
  the "one home" goal. Rejected.

## Testing

- Existing e2e suite is the test: all migrated specs pass on the new fixtures
  (`npm run test:e2e` locally — broad UI blast radius).
- `photo-serving.test.ts` keeps covering placeholder resolution from the new demo path.
- The label script needs no unit test of its own: every e2e run exercises it end-to-end
  (missing/broken output fails the specs immediately).

## Out of scope

- No change to the upload pipeline, photo-serving variants, or demo-collection seeding
  behavior (only paths move).
- No per-test-case images — per-spec-file granularity.
