## Where we are

**What Adored is.** A working Next.js 14 App Router app for *curatorial collection sorting*. A user creates collections, adds items (named or nameless, each with a per-collection catalog number), bulk-uploads photos into a durable per-collection **pool** and promotes them into items, runs a per-curator **sort session** (triage into Love / Like / Maybe / Onward tiers, then pairwise "which do you love more?" comparisons), generates a ranked **result** with manual override, and shares a finalized result via a public token link. It is well past MVP.

**Stack (verified against code):**

- **Next.js 14 App Router**, TypeScript strict, Server Components by default (`"use client"` only for interactive forms/hooks).
- **Drizzle ORM** over **Postgres** (Neon / Vercel Postgres) via the `postgres-js` driver (`src/lib/db.ts`); schema in `src/lib/db/schema.ts` — **15 `pgTable`s**.
- **NextAuth v4**, `DrizzleAdapter`, **JWT** session strategy (`src/lib/auth.ts:124`), dual providers (Credentials email+password with bcrypt; EmailProvider magic-link).
- **Vercel Blob** for photo storage (client-upload; local filesystem fallback in dev).
- **Vitest** (unit + DB-backed integration behind `RUN_DB_TESTS=1`), **Playwright** e2e (ephemeral Docker Postgres, multi-viewport), deployed on **Vercel**.

**Layered architecture (strictly server-first):**

```
src/app/**                 file-based pages + src/app/api/** route handlers (mutations)
  → src/server/api/*       thin controllers (one per resource)
    → src/server/services/* domain Services (Collection, Item, Photo, Session,
                            Scoring, Pairing, Preference, SortResult, Membership, …)
      → src/server/repositories/* interface-typed repos; implementations/* do the Drizzle calls
        → Drizzle / Postgres (src/lib/db.ts, schema.ts)
src/server/dal/*           authorization chokepoint-in-progress (collection-access.ts)
src/middleware.ts          withAuth route protection
```

Key invariants:

- **`decision_events` is the immutable, append-only source of truth.** Scores, preferences, and rankings are *lazily derived* — never stored as authority on the Item.
- **All mutations go through `src/app/api/**` routes** (no DB calls from the client). React calls APIs only.
- **`deletedAt` soft-delete** throughout (users are the exception — see decisions); a tombstoned catalog number is never reused. **Draft sort-results are the other exception — hard-deleted children-first** (`SortResultItemRepository.deleteByResult` → `SortResultRepository.delete`): they are derived/re-creatable state, and the `sort_result_items → sort_results` FK has no `ON DELETE` cascade, so children go first; it is not yet wrapped in a transaction (recoverable — a follow-up tightens this) — `purses-r7p`.
- **Item purge is the permanent hard-delete path** (`ItemPurgeService`, `purses-u3p`) — **owner-only** (`requireApiCollectionOwner`, the strict sibling of `requireApiCollectionAccess`). Children-first in one `withTransaction` (the `items` FK has no `ON DELETE CASCADE`): `CollectionPreferenceItem` rows + photos, then the item; photo **blobs are deleted best-effort *after* commit** (a `del` failure is logged, never rolls back — orphans are inert/sweepable). **Blocked with `409` when the item is referenced by any sort result** (draft or finalized); its owner-only companion `removeItemFromDraftResults` (`POST /api/items/[id]/remove-from-sorts`) detaches the item from **draft** results only (finalized + preferences untouched, a deliberate t9l exception) so it can then be purged. This is **decision 13's purge realized for items**; **collection purge (`CollectionPurgeService`) is now its collection-level sibling** (below). The item purge **writes one append-only `audit_log` row inside the same transaction** (`AuditLogRepository`, tx-bound by construction — `item.purge`, actor from the session, photo/preference counts), so a committed purge always carries its audit record.
- **`audit_log` is the append-only permanent-purge trail** (`purses-ite`). **No FKs** — it references purged item/collection ids as a standalone historical record; a composite `(collection_id, created_at, id)` index backs the owner-only, newest-first read at `GET /api/collections/[id]/audit`. Immutability is application-level (no `UPDATE`/`DELETE` path); the read `?limit=` is clamped server-side (≤200). `collection.purge` rows are written by `purgeCollection`, in the same transaction as its cascade.
- **Collection purge** (`CollectionPurgeService`, `purgeCollection`) is the collection-level sibling of item purge: a permanent **total-erase** of the whole collection in one `withTransaction`, deepest-child-first across all FK-linked tables (`sort_result_shares → sort_result_items → sort_results → decision_events → sessions → preferences → photos → items → invitations → memberships → the collection`, none with `ON DELETE CASCADE`), then a `collection.purge` audit row and best-effort post-commit blob deletes. **No `409` block** — it erases draft AND finalized results across all curators (the owner owns the whole collection). The route resolves the collection **including soft-deleted** (the `DELETE`→purge path) and requires the body to echo the **collection name**. The collection row is **hard-deleted** (not soft).
- **Multi-row result writes are transactional.** `createDraftResult` / `supersedeResult` wrap the `sort_results` row + all `sort_result_items` INSERTs in `withTransaction` (atomic; whole-transaction retry on the `UNIQUE(collection, number)` race) — `purses-nea`. **This is the codebase's first real transaction:** prod runs **postgres-js** (TCP), which supports interactive transactions, so the earlier *"neon-http has no transactions"* belief (still echoed in a few stale comments — follow-up bead) is wrong. `deleteResult` is the one remaining non-transactional multi-row write.

**Shipped features (verified):** collections CRUD with owner+membership model and real cover photos; items (named/nameless, catalog numbers, soft-delete, hero photos); photo pool + bulk upload with grouping and unified "Move to…" reassignment; per-curator triage→pairwise sort with the ScoringService model; computed results with manual override, finalize/supersede; tokenized public result sharing; email invitations with per-invite permission flags + member management; slug + sequential-number URLs (no raw ULIDs); NextAuth email+password and magic-link with JWT sessions and middleware protection; substantial security hardening (see Phase 9); Vitest + DB-integration + Playwright test infrastructure wired into CI.

**Item AND collection purge are now built** — `ItemPurgeService` + `POST /api/items/[id]/purge` (+ companion `remove-from-sorts`) and `CollectionPurgeService` + the rewired `POST /api/collections/[id]/purge` (whole-collection cascade); decision 13's hard-delete cascade — see persistence invariants above; `purses-u3p`. The old `purgeItem`/`purgeCollection` no-ops no longer govern. **The single DAL chokepoint and the Owner/Curator role collapse are now built** (epic `purses-pv9`, decision 17): `src/server/dal/capabilities.ts` (`CAPABILITIES` map + `requireApiCapability`) and the role-derived model shipped in PR3. **Not yet built (don't assume):** the per-route migration to `requireApiCapability` (PR4, `purses-g6o`) — routes still call the member-or-owner guards, so member/invitation management is not yet owner-only.

## How we got here

### Timeline (Phase 0 → Phase 9)

1. **Phase 0 — MVP v1 (2026-05-07).** The original "PurseInator" MVP built overnight: Next.js App Router, **Prisma** + Neon, Vercel Blob, Auth.js v5 magic-link, Resend; an **operator** (photographs/uploads) vs **curator** (ranks) split; Elo scoring with four result tiers. The design anchor was set on day one: *"Rachel isn't shopping — she's sorting through her life"* — safe, unhurried, judgement-free.
2. **Phase 1 — v1 hardening (2026-05-08 → 05-17).** Rebrand to "PurseInator", tablet-first refocus, client-side background removal, hosted demo. The structural change: the global JWT role was replaced with **hierarchical per-collection membership + invite tables**. CI made a correctness gate (ephemeral-Postgres e2e, smoke test, `/api/health`).
3. **Phase 2 — The Complete Refactor (2026-05-29 → 05-30).** A deliberate **blank slate** (`3342e84` removed all source, keeping only docs/.beads/.claude) restarted the app on a **service-first** architecture: persistence-agnostic Services → Drizzle Repositories → thin API handlers → React-only-calls-APIs. **Prisma → Drizzle**; ULID primary keys; **DecisionEvents immutable append-only truth**; buckets renamed to user-facing Love/Like/Maybe/Release.
4. **Phase 3 — GitHub Flow + Neon branch-per-environment (2026-06-01).** Triggered by a prod connection string leaking into `.env.local`: Neon isolated so **Production→`main` DB, all Previews + local dev→a long-lived `development` DB** (no per-PR branches — the simplest design that protects prod). GitHub Flow adopted; the e2e harness built and hardened. (This is where the `VERCEL=1` Secure-cookie gotcha was diagnosed — decision 3.)
5. **Phase 4 — First design-system attempts (2026-06-02 → 06-05).** Two warm/domestic directions tried and **rejected** ("The Lamplit Sitting Room", then "Cabana"): the warmth read as cozy, not gallery-grade. Owner's verdict — *"the colours are ugly / the whole system is wrong."*
6. **Phase 5 — TONE first-order + sort model + Luminous (2026-06-09).** The foundations reset in a single day: **TONE.md written as the first-order contract**; the **ScoringService reworked** (band-center seeding + asymmetric deltas); the visual system replaced with the **Luminous Gallery** (white ground, committed cool color as protagonist, Playfair + Inter, light+dark, "Brand never speaks Danger"). Fourth tier renamed Release→**Onward**.
7. **Phase 6 — Rename PurseInator → Adored (2026-06-10).** The placeholder name retired (#125) across display brand, technical identifiers, and living docs. History deliberately **not** rewritten (decision below / rename story).
8. **Phase 7 — Bulk upload → durable pool → grouped, numbered items (2026-06-13 → 06-14).** Metadata-first ordering **inverted**: dump images fast, group/name later or never. `items.name`/`photos.itemId` made nullable, per-collection catalog number added, **Blob client-upload** durable pool, gentle deferred-metadata surfacing. Adopted `adversarial-review` as a gate.
9. **Phase 8 — Real card images, covers, slugs, analytics (2026-06-14 → 06-16).** UI-fidelity + URL fixes: real hero/cover photos on cards; member-or-owner page IDOR fix (`purses-82r`); **short collection slugs** replaced raw ULIDs under "slug for nav, id for data" (#190). Playwright runs selectively on UI changes; analytics added.
10. **Phase 9 — Authz overhaul: close live cross-tenant holes (2026-06-17 → 06-18).** A security cluster closed verified live cross-tenant read/write/IDOR holes: shared `requireApiCollectionAccess` (#196), cross-curator triage scoped (#198), session/result URLs got numbers (#197), the whole `/api/sort-results` subtree guarded (#200), dead routes deleted (#201). The heavier DAL chokepoint was deliberately **deferred** to epic `purses-pv9` — security first, structure later.
11. **Phase 10 — "Sea Glass" theme refresh (2026-06-28).** The Luminous palette retuned without changing its bones. Light moved off pure white to a **cool sea-glass ground** (`#D3E2E5`; cards still rise to white); dark became **"Sea Glass at Night"** — one teal spine inverted toward black, raised planes lifted by an inset highlight + a luminous rim + a glow (*elevation by light, not a muddy mid-tone*). The spark went **citron → marigold** (`#EFCB77`), decor **mauve → soft violet** (`#B5AACC`, now used freely), and the dark primary **cornflower-blue → luminous teal** (`#4FB6C7`); new `content-deep` / `spark-soft` / `decor-soft` tokens; body type bumped to 17px and h1 to weight 700. `src/app/globals.css` is the source of truth; `DESIGN.md` updated to match.

### Decisions log

Each entry is **Decision / Rationale / Status**. Where design and shipped code diverged, that is stated explicitly.

**1. Blank-slate service-first refactor (Prisma → Drizzle, DecisionEvents immutable).**
- *Decision:* Wipe the source (`3342e84`) and rebuild as Services → Repositories → thin API handlers → React-calls-APIs; DecisionEvents append-only; scores/rankings lazily derived; ULID PKs.
- *Rationale:* Keeps the data model simple and authoritative and concentrates authorization server-side. The original Prisma stack and its onboarding/roles code were erased in one move rather than incrementally migrated.
- *Status:* **Shipped.** Layout verified: `src/server/{api,services,repositories,dal}`; `decision_events` in `schema.ts:203`.

**2. Auth: NextAuth v4 Credentials + magic-link; JWT sessions (design said DB).**
- *Decision:* NextAuth v4 + `@auth/drizzle-adapter`; **Credentials** (email+password, bcrypt) as the primary sign-in plus an EmailProvider magic-link path. The canonical NextAuth schema (`user`/`account`/`session`/`verificationToken`) forced renaming the legacy `users` table; **users hard-delete** (no `deletedAt`), collections/items keep soft-delete.
- *Rationale / divergence:* The auth **design specified database-backed sessions and a `session` table the app does not use as a session store** — the shipped code **pivoted to JWT** (`src/lib/auth.ts:124` `strategy: "jwt"`). And **prod magic-link email was never wired**: `sendVerificationRequest` only `console.log`s in development (`src/lib/auth.ts:78-80`), so the magic-link is dev-only despite the provider being configured.
- *Status:* **Shipped (with the two design-vs-code gaps above).** Credentials authorize at `auth.ts:31-62`; bcrypt at `:48`. The display **name is editable** via `PATCH /api/users/me` (name-only) and **carried through the JWT**: the `jwt`/`session` callbacks (`src/lib/auth-callbacks.ts`, extracted so they unit-test without the adapter's DB side-effect) seed `token.name` at sign-in and refresh it on `useSession().update()` (`trigger:"update"`, coercing `""`→`null` to match the DB), so a freshly-set name reflects without re-login (`purses-wew`).

**3. The `VERCEL=1`-in-`.env.local` `__Secure-` cookie gotcha.**
- *Decision:* Never let Vercel system vars (`VERCEL` / `VERCEL_ENV` / `VERCEL_URL` / `VERCEL_OIDC_TOKEN`) live in `.env.local`; neutralize `VERCEL` in the Playwright env block; **do NOT override `useSecureCookies`** (keep Vercel's native prod Secure detection).
- *Rationale:* `vercel env pull` wrote `VERCEL=1` into `.env.local`, which makes NextAuth emit a Secure-flagged `__Secure-next-auth.session-token` cookie that browsers **drop over `http://localhost`** → middleware's `getToken()` saw no session → every authenticated request bounced to `/login`. The bug was env hygiene, not auth code (incident #62, fix #64).
- *Status:* **Shipped + encoded as a startup guard.** `src/lib/env.ts:69-76` warns loudly when `VERCEL` is set and `AUTH_URL` is `http://` rather than overriding cookie behavior.

**4. Neon branch-per-environment.**
- *Decision:* `DATABASE_URL` scoped so **Production → `main` DB; all Previews + local dev → a long-lived `development` DB**. No per-PR ephemeral branches.
- *Rationale:* After a prod connection string leaked into `.env.local`, prod had to be unreachable from any non-production deploy. Per-PR branches were rejected as more machinery than needed — the simplest design that protects prod.
- *Status:* **Shipped** (topology lives in `docs/DEPLOYMENT.md` + the kept `neon-migration.md` history note).

**5. TONE.md first-order; Luminous design system accountable to it.**
- *Decision:* TONE.md is the **first-order, medium-agnostic** contract (constraints, never hexes/durations); DESIGN.md and copy answer to it; an exception is a written amendment to TONE. The Luminous Gallery delivers the feel; **"Brand never speaks Danger"** (red/amber/green reserved for ANSI Z535 safety meanings, never decorative); fourth tier **Release → Onward** ("Release"/"letting go" read clinical/grief-adjacent).
- *Rationale:* Two warm palettes were rejected as cozy-not-gallery; the durable fix was to make tone the contract and the visuals accountable to it. *"Restraint is not minimalism"* — Adored is aesthetic, not minimalist.
- *Status:* **Shipped (#82).** See `DESIGN.md`; tier tokens love/like/maybe/onward.

**6. Sort-ranking model: single [0,1] score, band-center seeding.**
- *Decision:* One continuous score in [0,1], computed in two order-independent passes. Triage seeds each item at its **tier-band center** (Love/Like/Maybe/Onward = **0.875 / 0.625 / 0.375 / 0.125**); pairwise refines with **asymmetric deltas (win +0.10, loss −0.05)** so rising is easier than falling (affirmation bias). Cross-tier override is emergent and symmetric (2 consistent wins promote, 3 losses demote); tie = no swing, skip = no-op.
- *Rationale:* The old edge-seeds read every tier one bucket too high (`seed→getBucket` was not an identity round-trip — `purses-7lh`), and a floored delta could never demote. Center-seeding makes `seed→getBucket` an identity round-trip and gives ±0.125 of pairwise headroom.
- *Status:* **Superseded by entry 24 (Epic 0).** The band-center **triage seed** survives (`ScoringService`'s `TIER_SEED`, still the item's `score`/bucket), but the **asymmetric pairwise deltas were retired** — pairwise no longer moves score; ordering within Love+Like is now a binary-insertion replay materialized as `order_rank`. `WIN_DELTA`/`LOSS_DELTA` no longer exist.

**7. Photo pool: upload-first, defer metadata; neon-http has no transactions.**
- *Decision:* Upload-first into a **durable per-collection pool** (`item_id IS NULL`), defer metadata, promote into grouped numbered items. Because **neon-http has no transactions**, the order is **create-item → assign-photos** (only partial failure = a harmless empty item), and assignment is a **single guarded `UPDATE … WHERE collection_id = c AND id IN ids AND item_id IS NULL AND deleted_at IS NULL`** whose **affected-row-count vs requested-count is the IDOR/double-assign guard**. **Hero is folded into the same UPDATE** (`is_hero = (id = heroPhotoId)`) so there is never a photos-but-no-hero window. Catalog number = `MAX(number)+1` with **retry-on-23505** (no txn to lock).
- *Rationale:* Getting photos in fast is the urgent real task; a stateless/transactionless driver means the WHERE clause and the count comparison *are* the integrity mechanism.
- *Status:* **Shipped.** `assignPooledPhotosToItem` + the explanatory comment at `src/server/repositories/implementations/PhotoRepository.ts:202-232` (returns count; caller compares); pre-check `countAvailablePooled` at `:240`; 23505 retry at `ItemRepository.ts:45-50` (`items_collection_number_unique`).

**8. Vercel Blob client-upload; `onUploadCompleted` can't reach localhost.**
- *Decision:* Bulk upload uses Blob **client-upload** (`@vercel/blob/client`) to bypass the 4.5 MB serverless body cap. The durable `photos` row is written **only** in the server `onUploadCompleted` callback, trusting the **signed `tokenPayload`** (never the client).
- *Rationale / divergence:* That callback **cannot reach `localhost`**, so the full path is verifiable **only on a Vercel preview deploy**, not local dev. The row-write was extracted into a pure `recordPooledPhoto` seam precisely so it is unit/DB-testable without Blob's network callback.
- *Status:* **Shipped** (pool/upload route + `recordPooledPhoto`).

**9. Reassign is one operation; hero reconciliation rules.**
- *Decision:* Move / split / return-to-pool are **one reassign**: set the selected photos' `item_id` (existing item = move, new item = split, `NULL` = return to pool). Hero rules: moved photos become non-hero on an existing target; the first moved photo is hero of a new item; the pool clears hero; a **source that loses its hero but keeps photos auto-promotes its first remaining photo**; **empty source items are left, not auto-deleted — for predictability**. `getNextCatalogNumber` maxes over **soft-deleted rows too** (a tombstoned number is never reused).
- *Rationale:* Treating the three gestures as one `item_id` reassignment is the smallest model; the deliberate "don't auto-delete empty sources" keeps behavior predictable rather than clever.
- *Status:* **Shipped.** `reassignPhotos` (`PhotoRepository.ts:259-284`, `targetItemId|null`); `getNextCatalogNumber` MAX-over-all-rows at `ItemRepository.ts:103-114`.

**10. URL model "slug for nav, id for data".**
- *Decision:* Collection page URLs use a human **slug**; session/result URLs use per-collection **sequential numbers**; **never raw ULIDs** in user-facing URLs. The slug/number resolves the entity **only at the page boundary**; every downstream DB query, image/file URL, client fetch prop, redirect, and integrity guard uses the immutable ULID.
- *Rationale:* **Slugs are globally unique (not per-owner)** *because* per-owner numbering would make a shared link resolve to a different collection for each viewer. A **reserved-slug blocklist** (e.g. `new`) exists *because* `/collections/new` is a static route Next resolves **before** the dynamic `[id]`. The **§7 audit rule**: every `params.id` downstream is wrong unless (a) passed to the access guard or (b) used as a nav href.
- *Status:* **Shipped** (#190 collections / #197 sessions+results). `RESERVED_COLLECTION_SLUGS = new Set(["new"])` at `src/lib/collections/slug.ts:7`.

**11. E2E testing strategy.**
- *Decision:* **Playwright over Cypress** (first-class multi-device emulation — iPad-landscape / iPhone-13 / desktop, WebKit ≈ iOS Safari). Test the **production build** (`next build && next start`), not `next dev`. Use an **ephemeral Docker Postgres on `:5433`** with a **hard guard that refuses any non-local host** (so it can never hit a Neon branch). **Mock the `@vercel/blob` boundary**; drive **only the Credentials provider** in the gate (magic-link needs an inbox).
- *Rationale:* The TRUNCATE in `resetDb()` must never touch a real DB — so the guard is a **fail-closed allowlist** (host ∈ {localhost, 127.0.0.1, ::1}), correct-by-construction rather than a denylist of three known Neon hosts.
- *Status:* **Shipped.** Guard at `e2e/fixtures/db.ts:14-39`; port `:5433` at `db.ts:12`; Credentials-only login in `e2e/auth.spec.ts`; blob stubbed in `e2e/sort-images.spec.ts`. Middleware public paths (`api/auth|login|signup|shared`) at `src/middleware.ts:8`.
- *Accessibility gate (`purses-sea`):* `@axe-core/playwright` scans the core screens in **both themes** for WCAG 2.x A/AA (`e2e/a11y.spec.ts`, tablet project — a11y is viewport-independent). Fails on **serious/critical**, reports moderate/minor; each scan logs its passing-check count so the gate can't silently no-op. This is the **rendered-DOM** backstop the token-pairing `src/lib/design/contrast.test.ts` can't be (a bad pair can't pass by omission). Limit: axe doesn't reliably automate **1.4.11 non-text** contrast — `contrast.test.ts` + the screenshot pass still own that.
- *Leaner test strategy (2026-07-09, `chore/test-prune`):* an audit found the suite mostly load-bearing but **CI-cost-heavy from viewport multiplication**, not test count. Changes: **(1) Viewport** — `playwright.config.ts` now runs **tablet only by default** (WebKit, the primary target, every spec); `PW_VIEWPORT=phone|desktop` runs ONLY that viewport for viewport-specific work (phone was WebKit-redundant with tablet; no spec uses touch/drag; per-viewport assertions live only in `layout.spec`). Default e2e dropped from ~181 spec-runs (3 viewports) to ~61 (tablet). **(2) Selective e2e** — a PR runs only the specs for its touched flows (the `changes` job's per-area `dorny/paths-filter` → the e2e job's area→spec map), with the `layout`/`smoke`/`a11y` floor always on; **blast-radius paths (`components/ui/**`, design tokens, `lib/db/**`, `server/**`, the e2e harness, deps) and merge-to-`main` force the FULL suite** — the safety net. **(4) Docs-only PRs run one job** (2026-07-11): `db-tests` is gated on a new `code` paths-filter output (`src/`, `drizzle/`, `e2e/`, `scripts/`, `bench/`, `public/`, `.github/workflows/`, `.githooks/`, root config globs). A change confined to `docs/`, `graphify-out/`, `.beads/`, `.claude/`, or the root governance `.md` files cannot affect a DB test, so Postgres never spins up for it; `coverage` needs `db-tests` to succeed, so it **skips in lockstep** — correct, since a docs-only change cannot move the floor. Net: a docs-only PR runs exactly **Lint, test, build**. The filter is positive-only and a deliberate **superset** (ambiguous paths like `public/`, `vercel.json`, and the workflows themselves over-trigger rather than risk skipping a suite that was needed); `!`-negation is unusable here, per the paths-filter note in `ci.yml`. `deploy-report`'s coverage-artifact download is now `continue-on-error` (the artifact is absent on a docs-only push to `main`; the assemble step already no-ops on an empty dir, leaving the last published coverage in place). Note for whoever finally adds `Merged coverage floor` to branch protection (see below): a **skipped** job satisfies a required check, so this does not deadlock docs-only PRs. **(3) Tier principle** (global CLAUDE.md): DB-integration is for real-DB crossings/integrity/authz-boundary only (FK/unique/CHECK, tx/rollback, advisory locks, cascade, SQL semantics, stranger 403/404) — one un-mocked crossing per route, not per branch; branch logic + copy live in unit tests; e2e is the full-stack journey at one viewport. Copy-inventory / register-scan / tautology tests were pruned.

**12. Deferred-metadata TONE guardrails (NON-NEGOTIABLE).**
- *Decision:* When surfacing items that "could use details": **no counts of incompleteness, no completion %/progress bar, no warning styling**; **person-side copy** ("Add a name" / "Tell its story", never "Incomplete"/"Missing"); **"could use details" = `name IS NULL` only** (a name turns a row into a story; brand/material/dimensions are optional extras, not deficiencies).
- *Rationale:* A direct expression of TONE — invitation, never nag; one thing at a time; no shaming metrics. This is a tone contract, not a styling preference, hence non-negotiable.
- *Status:* **Shipped.** `filterItems` / `hasName` use name-only (`src/lib/items.ts:9,27-33`); the "Waiting for a name" filter is off-by-default and opt-in (`?unnamed=1`).

**13. Authorization direction.**
- *Decision:* Today: a shared `requireApiCollectionAccess` (member-or-owner) plus curator-ownership guards; **owner-without-a-membership-row is authorized**. Heading toward a **single DAL chokepoint** + an **Owner/Curator role collapse** replacing the 9 permission flags (epic `purses-pv9`). **18. Account deletion = purge owned data + scrub PII (pv9 PR6, `purses-hybm`).**

**22. Session-uniqueness redesign: `sessions_active_unique` becomes a PARTIAL index — one IN-PROGRESS session per slot (Epic C, purses-4bhh/ydeu, migration 0009). Supersedes entry 21's interim mitigation.**
- *Decision:* Migration `0009` replaces the unconditional `UNIQUE(collection_id, curator_id)` with a **PARTIAL unique index** (`WHERE deleted_at IS NULL AND status IN ('active','paused')`), so the database enforces only **one IN-PROGRESS session per `(collection, curator)` slot**. Terminal (`completed`/`abandoned`) and soft-deleted (`set_aside`) rows **fall out of the predicate and free the slot** — a curator can start a new sort after completing, abandoning, or setting aside the previous one. The cap changes from *"one session per slot ever"* to *"unbounded historical rows, one in-progress"* (auth-gated, owner/curator only). **Predicate↔guard invariant — all three writers that move a row INTO the partial predicate catch the `23505` → `CurrentSessionExistsError` → `409` (never a `500`):** (1) `create()` (a fresh `active` row into an occupied slot), (2) `restore()` (undo set-aside re-enters as `active` while a newer in-progress session holds the slot), and (3) `update()` (a `PATCH {status}` terminal→`active`/`paused` transition re-entering the predicate). `restoreSession` adds a friendly pre-check (`findInProgress` widens `findActive` to `status IN (active,paused)`) that returns the `409` BEFORE the UPDATE; the repo's `restore()`/`update()`/`create()` catches are the race backstops. **Serialization gotcha:** drizzle-kit 0.20.17 (snapshot v5) cannot serialize a partial-index predicate, so `0009` is **hand-authored**; `schema.ts` carries the `.where()` only to record the intended truth (the generated snapshot can't encode it — `db:generate` emits nothing for this change, so the SQL is the source of truth). The migration is **forward-only** (no safe down — recreating the unconditional index would `23505` once >1 terminal/soft-deleted row per slot exists). The defense-in-depth UI gate + 23505→409 net from entry 21 are kept.
- *Rationale:* Entry 21's unconditional index over-constrained the model — it forbade a curator from *ever* starting a second sort of a collection, even after the first was completed or set aside, which is the normal flow (purses-4bhh root fix). A partial index expresses the real invariant ("one live sort at a time") in the database itself, where it can't be bypassed. The three-writer catch is the **predicate↔guard contract**: every code path that could push a second row into the predicate must translate the unique violation into the same gentle, typed `409`, so a race or direct-API call is never a raw `500`. The pre-check makes the common case (you set this aside, then started a new sort, then hit undo) decline gently — the set-aside session stays set aside — without relying on the DB error alone.
- *Status:* **Shipped (Epic C).** Migration `drizzle/0009_partial_active_session.sql`; the `activeIdx` `.where()` in `src/lib/db/schema.ts`; `create`/`restore`/`update` 23505 catches + `findInProgress` + `isCurrentSessionConflict` in `src/server/repositories/implementations/SessionRepository.ts`; `restoreSession` pre-check in `src/server/api/sessions.ts`; `errorResponse` 409 mapping (`src/server/api/http-errors.ts`). - *Status:* **Shipped (kg/UX-review).** Workspace + components `src/app/collections/[id]/page.tsx`, `src/features/collections/{PhotoPoolPreview,ItemPreviewGrid,workspaceState,CollectionCard}.tsx`; bounded reads in `PhotoRepository`/`ItemRepository` (+ impls) and `src/server/api/{photos,items}.ts`; cue query `findCollectionIdsWithPooledPhotos` + `src/lib/db/collection-pool-cue.integration.test.ts`; pool/item preview DB tests under `src/lib/db/`. **24. Ranking overhaul: Elo pairwise → binary-insertion recompute-from-log (Epic 0, 2026-06-30, migrations 0010–0012).**
- *Decision:* The Elo/pairwise **score-delta** ranking (entry 6) was replaced by **deterministic binary-insertion ranking derived from the append-only `decision_events` log**. Pairwise comparisons no longer nudge a score; instead the Love+Like items (`top`+`high` buckets) are ordered by a binary-insertion **replay** of the comparison log (`deriveOrder`/`placeItem`, `bounded binary-search placement with tie/skip`), and that order is materialized onto a new nullable `preferences.order_rank` (dense per curator). Triage still seeds the item's `score`/bucket (band-center `TIER_SEED` survives); only the pairwise deltas are gone. Two schema additions (migrations 0010/0011): `preferences.order_rank` (nullable int) with a **partial unique index** `(collection_id, curator_id, order_rank) WHERE order_rank IS NOT NULL` (NULL = loved-but-uncompared, no order), and `decision_events.client_key` (nullable text) with a **partial unique index** `(session_id, client_key) WHERE client_key IS NOT NULL` as an **idempotency key** for `POST …/decisions` (legacy NULL rows exempt). `preferences.score`/`confidence` are retained (NOT NULL). Finalize (`sortResultMaterialization`) sorts **bucket priority → `order_rank` ascending (NULLS LAST) → `itemId`**. Migration **0012** is a **forward-only clean reset**: it discards every Elo-era **DRAFT** `sort_results` (children first, FK order) so no draft can finalize with a dead Elo `computed_rank`; finalized snapshots are immutable and untouched. The dead `PairingService` was deleted.
- *Rationale:* Recompute-from-log keeps the append-only event log the single source of truth (entry 1) while giving a stable, explainable order that a score-delta model couldn't. The idempotency key makes a retried/duplicated decision POST safe under the client's at-least-once delivery; the `FOR UPDATE` session-row lock (see API.md) serializes a curator's concurrent recomputes. The 0012 reset is forward-only because an Elo-derived draft rank has no meaning under the new model — cheaper and safer to require a fresh recompute than to migrate stale draft order.
- *Status:* **Shipped (Epic 0).** `deriveOrder`/`placeItem`; `ScoringService` (triage seed only, pairwise delta removed); `PreferenceStateService.deriveOrderRanks` + `clearOrderRanks`; `sortResultMaterialization` (bucket→orderRank NULLS LAST→itemId); `POST /api/sessions/[id]/decisions` (clientKey idempotency + `FOR UPDATE`); migrations `0010_mighty_photon`, `0011_orderrank_clientkey_partial_indexes`, `0012_reset_elo_drafts`. DB tests: `src/lib/db/binary-insertion-ranking.integration.test.ts`.

**26. Auth: NextAuth v4/JWT → better-auth (DB sessions) (`feat/better-auth-migration`, `purses-74tx`). Supersedes entries 2 & 3's mechanism.**
- *Decision:* Replace NextAuth v4 (Credentials + EmailProvider, **JWT** session — entries 2/3) with **better-auth** backed by **database sessions**. Three sign-in methods: **email+password**, **magic-link** (Resend, reusing `src/lib/email.ts`), and **Google** social. The whole auth surface is one better-auth catch-all handler at **`/api/auth/[...all]`** (`toNextJsHandler`), mounted at `basePath: "/api/auth"` — so the Google callback is `…/api/auth/callback/google`. The old `/api/auth/[...nextauth]` and `POST /api/auth/signup` routes are **deleted**; sign-up is now `POST /api/auth/sign-up/email`. `src/lib/auth.ts` becomes a thin **read façade** (`getSession`/`requireAuth`) that projects better-auth's `{ session, user }` down to the byte-identical **`{ user: { id, email, name } }`** contract the ~249 call sites and the DAL authz chokepoint already depend on — so **neither the call sites nor the chokepoint changed**. Session cookie-cache is left **off**, so every `getSession` is a fresh per-request DB read (a display-name edit shows on the next request; no stale JWT claim to invalidate). Middleware (`src/middleware.ts`) is an **optimistic** `getSessionCookie` **presence** check (no DB read at the edge) for the login-redirect UX only — real enforcement stays in the DAL. Schema collapses to the **canonical better-auth tables** `user`/`account`/`session`/`verification` (migration **0015**): the password now lives on **`account`** (scrypt, not on `user`), there is **no NextAuth `verificationToken`**, and no JWT. `UserRepository.purgeAndScrub` (account deletion, entry 18) was reworked to this shape: hard-delete `account` (holds the password) + `session` + `verification` (for the old email) rows, then tombstone the `user` row's `email`/`name`, `image`→null, `email_verified`→false.
- *Rationale / divergence:* Entry 2 recorded that the original auth design *specified* DB-backed sessions but the shipped code pivoted to JWT, and that prod magic-link was never wired — this migration closes **both** gaps: DB sessions are now real, and magic-link goes through the live Resend transport. DB sessions (over JWT) give server-side revocation and name-freshness without a token-refresh dance; the façade contract means the migration is a backend swap invisible above `auth.ts`. Migration 0015 is a **forward-only clean reset** (spec §9: no real users/data to preserve): it TRUNCATEs all app+auth data, drops the `ba_*` mirror tables and the old NextAuth `account`/`session`/`verificationToken`/`user`, recreates the canonical four, and re-points the six domain FKs to the new `user` — a data migration was unnecessary and riskier than a reset. Google client id/secret default to empty strings so the provider stays registered but inert until configured (the app still boots); rate-limiting is on in prod but disabled for loopback base URLs so the e2e suite's many same-IP sign-ins don't trip 429.
- *Status:* **Shipped (`feat/better-auth-migration`).** `src/lib/auth-server.ts` (the `betterAuth` instance), `src/lib/auth.ts` (façade), `src/lib/auth-client.ts`, `src/app/api/auth/[...all]/route.ts`, `src/middleware.ts`, `src/lib/db/schema.ts` (`user`/`account`/`session`/`verification`), migration `0015_collapse_to_canonical_better_auth_user.sql`, `UserRepository.purgeAndScrub`. Tests: `src/lib/auth.test.ts`, `src/lib/auth-server.test.ts`; e2e drives `sign-up/email`/`sign-in/email`/`get-session` (`e2e/auth.setup.ts`, `e2e/fixtures/better-auth.ts`).

**27. Batched decision pipeline: optimistic client queue + one-recompute batch route (Epic P, `purses-5mxt`, 2026-07-06).**
- *Decision:* No tap in any sort round waits on the database. Round taps (triage decisions, "Not mine"/"Not yet" dispositions, compare answers) enqueue into a **localStorage-persisted client queue** (versioned, curator-keyed envelope `adored.pending.v1.{curatorId}.{sessionId}`; synchronous persist **before** the UI advances) drained by a **single-flight flusher** (promise-shared per realm; **Web Locks** for cross-tab exclusion; strictly sequential, order-preserving; backoff 1 s/4 s/15 s/60 s; full failure taxonomy incl. per-entry disposition-409 rejection and 400-quarantine so no poison entry jams the queue). Contiguous decision runs go to **`POST /api/sessions/[id]/decisions/batch`** (≤50/batch): one advisory-lock transaction — semantic item validation (per-entry `rejected`), clientKey idempotency (SELECT authoritative under the lock + `ON CONFLICT … DO NOTHING` defense-in-depth), array-order inserts with **monotonic-ULID event ids** sharing the transaction's `defaultNow()` timestamp, then **ONE preference recompute** (only if ≥1 inserted). One shared `(createdAt, id)` comparator (`src/lib/decision-order.ts`) now backs both latest-wins consumers. Crash/pause recovery: `PendingDecisionsGate` on every sort/results surface drains pending queues **before** children mount (bounded ~5 s, then availability wins), plus a 30-day storage GC. Compare submits through the same queue as an idempotent batch-of-1; the triage round is a fully optimistic client component over a server-selected whole-remainder queue (`selectTriageQueue`), with one `router.refresh()` at round end and a recap merged from server events + pending entries. The single decisions route survives as compat fallback (its dead 23505 catch-and-re-read removed — a mid-tx re-read would 25P02; the advisory lock makes the race unreachable).
- *Rationale:* Every decision previously paid POST → advisory lock → full event-log replay → delete-all-then-insert → `router.refresh()` while the user waited — the same felt slowness in all three sort locations, and fatal to the usage round's quick pacing (parent epic `purses-9v1f`). Batching amortizes the recompute 50→1 (`npm run bench:batch`); the event log's append-only latest-wins semantics make the whole ladder (tap → localStorage → batch → `decision_events`) idempotently replayable via `clientKey`, so crash recovery is a re-flush, not a restore. Design: `docs/superpowers/specs/2026-07-06-epicP-batched-decisions-design.md` (adversarially reviewed, 34 findings folded — incl. the ItemId-format block, DB `now()` as the single ordering clock, and the disposition-409 split).
- *Status:* **Shipped (`feat/sort-unification-specs`).** Route `src/app/api/sessions/[id]/decisions/batch/route.ts`; `src/lib/{decision-batch-schema,decision-order,read-json-with-limit,web-lock}.ts`; `src/features/sorting/{decisionQueue,decisionFlusher,TriageRound,PendingDecisionsGate,pendingNotices}.tsx?`; `generateOrderedIdFactory` in `src/lib/id.ts`. Playwright crash-reload/pagehide coverage deferred, gated on e2e-as-required-check (`purses-yuw`).

**28. Usage as a second decision axis on the Epic P pipeline — derived at read time, recompute-skipped (Epic R PR 1 dark backend, `purses-sisy`, 2026-07-08).**
- *Decision:* "Do you use this?" is a **third `decision_events.type` (`usage`)**, purely additive — **no migration** (`type` is `text`, `decision` is `jsonb`). A `usage` event `{ itemId, result: "uses" | "not_uses" }` rides the **same** batched pipeline, clientKey idempotency, advisory lock, and flusher as triage/compare, but **never triggers a preference recompute and never clears a disposition**: the batch route gates both on a new **`insertedScoringCount`** (inserted entries with `type !== "usage"`), the single route on `body.type !== "usage"`. Usage is a **second axis, not a third tier** — it never touches `score`/`orderRank` (the scorer already type-filters both passes, so a usage event in the log is inert to scoring; proven by a differential invariance test). Usage is **derived at read time** (no projection table): `deriveUsage` folds the log latest-wins via the one shared `(createdAt, id)` comparator; the round queue and hub ladder both consume it through **one** cross-session read — `loadCuratorDecisionEvents`, the single definition of "the curator's decision log" (extracted verbatim from `PreferenceStateService.loadDecisionEvents`), exposed as `DecisionController.listForCurator`. A usage event for a **disposed but still-live item** is accepted (cross-device race, parent D3); non-live itemIds fall out at read time (the single route, like triage, does not validate `itemId` against the live set — pre-existing `purses-stln`, inert here because `deriveUsage` filters).
- *Rationale:* Usage must be as cheap and crash-safe as triage for the round's quick pacing, so it reuses the shipped ladder rather than a parallel path; skipping the recompute is pure waste-avoidance (the scorer ignores usage anyway, but `recalculatePreferences` still clears every `orderRank` + bulk-upserts the whole set inside the advisory lock). Deriving at read time keeps the model append-only and lets Standing / round / hub never disagree about "known". This PR is **dark and revert-safe** — no client emits `usage` yet; **PR 2 (the round UI) must land strictly after this PR is *deployed*** (a usage-writing client against a pre-PR-1 server gets a whole-batch 400 → the flusher quarantines the chunk). Design: `docs/superpowers/specs/2026-07-07-epicR-usage-round-design.md` (rev 2, adversarially reviewed, 18 findings folded).
- *Status:* **PR 1 shipped dark (`feat/epicR-usage-dark`).** `src/lib/derive-usage.ts`, `src/server/services/decision-log.ts`, `DecisionController.listForCurator` (`src/server/api/decisions.ts`), both `decisions` routes, `src/types/domain.ts`, `src/lib/decision-batch-schema.ts`; `DecisionEventRepository` widened to carry usage rows. **PR 2 shipped (`feat/epicR-usage-round`)** — the round UI + hub: `UsageRound` (write-nothing passes, at-most-twice cycling, Quick pacing + a11y floor) on a refactor-extracted `useOptimisticRound` hook (`TriageRound`'s machinery, now shared), `selectUsageQueue`/`usage-round-prefs`, the usage page (one `listForCurator` read, empty recap payload — DATA-6), the hub recommendation ladder (`recommendNextRound`: triage→usage→compare→decide + `whenUsageDemoted` never-re-promote + device-local demotion swap + third card), round-length change (30 s–5 m, default 2 m, `RoundLengthChooser` mid-round switch, "No timer" first-class), arc renames (person-side "Get acquainted"/"Which do you love more?"; `/welcome` keeps a neutral "A sorting round" noun), the 4-step arc, and `whatMoved()` usage counts. Recap decisions are deduped latest-wins so a revisit-after-ack never double-counts. Playwright usage smoke ships; the reload half stays deferred (`purses-hmjs`).

**29. Standing shows a second axis (usage chip) + draft results become hand-orderable (Epic S, `purses-mvn5`, migration 0016, 2026-07-11).**
- *Decision:* Two additive Standing features. **(a) Per-item usage chip** — "In your life" / "Resting" (count-free, first-order TONE) on the ranked composition, never on the most-loved hero. The **live Decide surface** (`/collections/[id]/results`) derives it at read time via the same `deriveUsage` over `DecisionController.listForCurator` (decision 28), while a **specific result** (draft OR finalized, `/results/[resultNumber]`) reads a **frozen snapshot**: new nullable column `sort_result_items.usage` (migration 0016, `text`), stamped at draft **materialization** by `SortResultService.createDraftResult` (folds the curator log through `deriveCuratorUsage`) and **fresh-folded on revision**, so a result is a keepsake of what was known when it was made, not a live query. Finalize never touches `usage`. **(b) Manual re-rank of draft results** — a `PATCH /api/sort-results/[id]/items` **transactional bulk endpoint** (body `{ order: [{ rid, manualRank }] }`, `requireApiResultAccess`, **409 when finalized**) writes 1-indexed `manualRank` for the whole sequence in one `withTransaction`; `DELETE` resets the overlay (NULLs every `manualRank`, back to the suggested order). The UI (`RerankPanel`) offers **drag + move-up/down** with ≥44px targets, a `role=status` "Moved {name} to position N of M" announcement, and reduced-motion support. **Cross-tier hand-order shipped (`purses-9v1f.1`):** the reorder list spans both tiers as ONE ordered sequence with a real sentinel divider element; zone is derived **purely from position** relative to the sentinel (so `manualRank` and zone can't disagree — monotonic by construction), and a move across it writes `manualBucket` (`"low"`/`"medium"`/`null`) alongside `manualRank` in the same bulk PATCH (required-nullable = full overlay, so a null clears a stale override). The sentinel is AT-perceivable and each row exposes its group membership (WCAG 1.3.1). Design + adversarial review (R1–R4 folded): `docs/superpowers/specs/2026-07-11-epicS-cross-tier-handorder-design.md`.
- *Rationale:* Standing must answer "what do I love?" and "what's in my life?" without turning into a count/inventory, so usage rides as a quiet annotation, not a tier. The snapshot-vs-live split is deliberate: a finalized keepsake that silently re-queried usage would drift from the moment it recorded, so result rows freeze it while the always-current Decide page stays live. Bulk-transactional re-rank (not per-row PATCH) keeps a multi-move reorder atomic — a partial sequence is never persisted — and the 409-on-finalized guard makes the immutable-keepsake invariant a server contract, not just UI. Design: `docs/superpowers/specs/2026-07-…-epicS-standing-rerank-design.md` (rev 2, adversarially reviewed).
- *Status:* **Shipped (`feat/epicS-standing-rerank`).** `drizzle/0016_sturdy_the_professor.sql`; `sort_result_items.usage` + `SortResultItemRepository`; `SortResultService.createDraftResult`/revision fold; `src/app/api/sort-results/[id]/items/route.ts` (PATCH/DELETE); `RerankPanel` + `rerank-copy`/`usage-chip-copy`; the bulk PATCH/DELETE registered in the stranger-enumeration authz backstop.
