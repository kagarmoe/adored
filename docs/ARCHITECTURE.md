## Where we are

**What Adored is.** A working Next.js 14 App Router app for *curatorial collection sorting*. A user creates collections, adds items (named or nameless, each with a per-collection catalog number), bulk-uploads photos into a durable per-collection **pool** and promotes them into items, runs a per-curator **sort session** (triage into Love / Like / Maybe / Onward tiers, then pairwise "which would you reach for first?" comparisons), generates a ranked **result** with manual override, and shares a finalized result via a public token link. It is well past MVP.

**Stack (verified against code):**

- **Next.js 14 App Router**, TypeScript strict, Server Components by default (`"use client"` only for interactive forms/hooks).
- **Drizzle ORM** over **Postgres** (Neon / Vercel Postgres) via the `postgres-js` driver (`src/lib/db.ts`); schema in `src/lib/db/schema.ts` — **15 `pgTable`s**.
- **better-auth** with **database sessions** (not JWT), one catch-all handler at `/api/auth/[...all]`; Google is the only supported product login. `src/lib/auth.ts` is a thin read façade (`getSession`/`requireAuth`) over `src/lib/auth-server.ts`. **NextAuth, the `DrizzleAdapter`, the JWT strategy and `bcryptjs` are all gone** (decision 26; `bcryptjs`/`@types/bcryptjs` removed from `package.json`).
- **Local dev auth bypass:** `npm run dev` sets `AUTH_BYPASS=1` and `NEXT_PUBLIC_AUTH_BYPASS=1`. `src/lib/auth.ts` honors the server flag only when `NODE_ENV=development`, returning a development user (`dev@adored.test` by default) and creating that `user` row if needed. `src/lib/auth-client.ts` uses the public flag to read that same server-backed user from `/api/users/me`, so client chrome shows the profile affordance. `src/proxy.ts` skips only the optimistic login redirect under the same dev-only gate; production/build/start do not inherit the bypass.
- **Vercel Blob** for photo storage (client-upload; local filesystem fallback in dev).
- **Vitest** (unit + DB-backed integration behind `RUN_DB_TESTS=1`), **Playwright** e2e (ephemeral Docker Postgres, multi-viewport), deployed on **Vercel**.

**Layered architecture (strictly server-first):**

```
src/app/**                 file-based pages + src/app/api/** route handlers (mutations)
  → src/server/api/*       thin controllers (one per resource)
    → src/server/services/* domain Services (Collection, Item, Photo, Session,
                            Scoring, Pairing, Preference, SortResult, Membership, …)
      → src/server/repositories/* interface-typed repos; implementations/* do the Drizzle calls
        → Drizzle / Postgres (src/lib/db.ts, schema.ts)
src/server/dal/*           authorization chokepoint-in-progress (collection-access.ts)
src/proxy.ts               optimistic login-redirect (Next 16 proxy convention);
                           `/tutorials/*` + `/onboarding/*` are public tutorial
                           surfaces, while real app authz stays in DAL guards;
                           `npm run dev` disables only this redirect layer via
                           the local-only AUTH_BYPASS gate
```

Key invariants:

- **`decision_events` is the immutable, append-only source of truth.** Scores, preferences, and rankings are *lazily derived* — never stored as authority on the Item.
- **All mutations go through `src/app/api/**` routes** (no DB calls from the client). React calls APIs only.
- **`deletedAt` soft-delete** throughout (users are the exception — see decisions); a tombstoned catalog number is never reused. **Draft sort-results are the other exception — hard-deleted children-first** (`SortResultItemRepository.deleteByResult` → `SortResultRepository.delete`): they are derived/re-creatable state, and the `sort_result_items → sort_results` FK has no `ON DELETE` cascade, so children go first; it is not yet wrapped in a transaction (recoverable — a follow-up tightens this) — `purses-r7p`.
- **Item purge is the permanent hard-delete path** (`ItemPurgeService`, `purses-u3p`) — **owner-only** (`requireApiCollectionOwner`, the strict sibling of `requireApiCollectionAccess`). Children-first in one `withTransaction` (the `items` FK has no `ON DELETE CASCADE`): `CollectionPreferenceItem` rows + photos, then the item; photo **blobs are deleted best-effort *after* commit** (a `del` failure is logged, never rolls back — orphans are inert/sweepable). **Blocked with `409` when the item is referenced by any sort result** (draft or finalized); its owner-only companion `removeItemFromDraftResults` (`POST /api/items/[id]/remove-from-sorts`) detaches the item from **draft** results only (finalized + preferences untouched, a deliberate t9l exception) so it can then be purged. This is **decision 13's purge realized for items**; **collection purge (`CollectionPurgeService`) is now its collection-level sibling** (below). The item purge **writes one append-only `audit_log` row inside the same transaction** (`AuditLogRepository`, tx-bound by construction — `item.purge`, actor from the session, photo/preference counts), so a committed purge always carries its audit record.
- **`audit_log` is the append-only permanent-purge trail** (`purses-ite`). **No FKs** — it references purged item/collection ids as a standalone historical record; a composite `(collection_id, created_at, id)` index backs the owner-only, newest-first read at `GET /api/collections/[id]/audit`. Immutability is application-level (no `UPDATE`/`DELETE` path); the read `?limit=` is clamped server-side (≤200). `collection.purge` rows are written by `purgeCollection`, in the same transaction as its cascade.
- **Collection purge** (`CollectionPurgeService`, `purgeCollection`) is the collection-level sibling of item purge: a permanent **total-erase** of the whole collection in one `withTransaction`, deepest-child-first across all FK-linked tables (`sort_result_shares → sort_result_items → sort_results → decision_events → sessions → preferences → photos → items → invitations → memberships → the collection`, none with `ON DELETE CASCADE`), then a `collection.purge` audit row and best-effort post-commit blob deletes. **No `409` block** — it erases draft AND finalized results across all curators (the owner owns the whole collection). The route resolves the collection **including soft-deleted** (the `DELETE`→purge path) and requires the body to echo the **collection name**. The collection row is **hard-deleted** (not soft).
- **A purge takes the same advisory lock the decision writers take.** `ItemPurgeService` and `CollectionPurgeService` both call `lockCollectionCurators(tx, collectionId)` (`src/server/services/purge-lock.ts`) as the **first statement inside their `withTransaction`**. `recalculatePreferences` is a check-then-act (read the collection's live items → bulk-upsert preference rows for them), and `preferences.item_id` has **no `ON DELETE CASCADE`** — so a purge committing in that window deleted an item the upsert was about to reference and killed the curator's decision on a `23503` (a `500` mid-decision). The decision/disposition writers already serialize on `lockCollectionCurator` (`pg_advisory_xact_lock(hashtext(collection), hashtext(curator))`); the purge takes the **same lock on the same key scheme** — but for **every** principal authz lets recompute the collection (owner **union** members), because the lock key is per-curator while a purge is collection-wide and the actor is the *owner* (an actor-keyed lock wouldn't block a collaborator's recompute at all). The locks are acquired **ordered by `hashtext(curator_id)`**, so two concurrent purges of one collection can't deadlock-cycle; being `xact` locks, they release at commit/rollback. Pinned by `src/lib/db/purge-recompute-lock.integration.test.ts`.
- **Sequential-number / slug allocation is one shared primitive.** The MAX+1-then-retry-on-`23505` idiom (there is no lock to take for a per-parent unique value) was duplicated across five repositories; it is now `allocateWithRetry(attempt, isRetryableConflict, attempts = 5)` (`src/server/repositories/allocateWithRetry.ts`) — recompute the value *inside* `attempt`, retry **only** the constraint a fresh value can resolve, and stay **bounded** so a persistent conflict surfaces instead of spinning. Used by `ItemRepository` (catalog number), `SessionRepository` (session number), `SortResultRepository` (result number), and `CollectionRepository` (twice: collection number + slug).
- **Multi-row result writes are transactional.** `createDraftResult` / `supersedeResult` wrap the `sort_results` row + all `sort_result_items` INSERTs in `withTransaction` (atomic; whole-transaction retry on the `UNIQUE(collection, number)` race) — `purses-nea`. **This is the codebase's first real transaction:** prod runs **postgres-js** (TCP), which supports interactive transactions, so the earlier *"neon-http has no transactions"* belief (still echoed in a few stale comments — follow-up bead) is wrong. `deleteResult` is the one remaining non-transactional multi-row write.

**Shipped features (verified):** collections CRUD with owner+membership model and real cover photos; items (named/nameless, catalog numbers, soft-delete, hero photos); photo pool + bulk upload with grouping and unified "Move to…" reassignment; per-curator triage→pairwise sort with the ScoringService model; computed results with manual override, finalize/supersede; tokenized public result sharing; email invitations with per-invite permission flags + member management; slug + sequential-number URLs (no raw ULIDs); better-auth Google sign-in with **database** sessions and middleware protection (decision 26); substantial security hardening (see Phase 9); Vitest + DB-integration + Playwright test infrastructure wired into CI.

**Item AND collection purge are now built** — `ItemPurgeService` + `POST /api/items/[id]/purge` (+ companion `remove-from-sorts`) and `CollectionPurgeService` + the rewired `POST /api/collections/[id]/purge` (whole-collection cascade); decision 13's hard-delete cascade — see persistence invariants above; `purses-u3p`. The old `purgeItem`/`purgeCollection` no-ops no longer govern. **The single DAL chokepoint and the Owner/Curator role collapse are now built** (epic `purses-pv9`, decision 17): `src/server/dal/capabilities.ts` (`CAPABILITIES` map + `requireApiCapability`) and the role-derived model shipped in PR3. **Not yet built (don't assume):** the per-route migration to `requireApiCapability` (PR4, `purses-g6o`) — routes still call the member-or-owner guards, so member/invitation management is not yet owner-only.

## How we got here

### Timeline (Phase 0 → Phase 9)

1. **Phase 0 — MVP v1 (2026-05-07).** The original "PurseInator" MVP built overnight: Next.js App Router, **Prisma** + Neon, Vercel Blob, Auth.js v5 magic-link, Resend; an **operator** (photographs/uploads) vs **curator** (ranks) split; Elo scoring with four result tiers. The design anchor was set on day one: *"Rachel isn't shopping — she's sorting through her life"* — safe, unhurried, judgement-free.
2. **Phase 1 — v1 hardening (2026-05-08 → 05-17).** Rebrand to "PurseInator", tablet-first refocus, client-side background removal, hosted demo. The structural change: the global JWT role was replaced with **hierarchical per-collection membership + invite tables**. CI made a correctness gate (ephemeral-Postgres e2e, smoke test, `/api/health`).
3. **Phase 2 — The Complete Refactor (2026-05-29 → 05-30).** A deliberate **blank slate** (`3342e84` removed all source, keeping only docs/.beads/.claude) restarted the app on a **service-first** architecture: persistence-agnostic Services → Drizzle Repositories → thin API handlers → React-only-calls-APIs. **Prisma → Drizzle**; ULID primary keys; **DecisionEvents immutable append-only truth**; buckets renamed to user-facing Love/Like/Maybe/Release.
4. **Phase 3 — GitHub Flow + Neon branch-per-environment (2026-06-01).** Triggered by a prod connection string leaking into `.env.local`: Neon isolated so **Production→`main` DB, all Previews + local dev→a long-lived `development` DB** (no per-PR branches — the simplest design that protects prod). GitHub Flow adopted; the e2e harness built and hardened. (This is where the `VERCEL=1` Secure-cookie gotcha was diagnosed — decision 3.)
5. **Phase 4 — First design-system attempts (2026-06-02 → 06-05).** Two warm/domestic directions tried and **rejected** ("The Lamplit Sitting Room", then "Cabana"): the warmth read as cozy, not gallery-grade. Owner's verdict — *"the colours are ugly / the whole system is wrong."*
6. **Phase 5 — TONE first-order + sort model + Luminous (2026-06-09).** The foundations reset in a single day: **TONE.md written as the first-order contract**; the **ScoringService reworked** (band-center seeding + asymmetric deltas); the visual system replaced with the **Luminous Gallery** (white ground, committed cool color as protagonist, Playfair + Inter, light+dark, "Brand never speaks Danger"). Fourth tier renamed Release→**Onward**.
7. **Phase 6 — Rename PurseInator → Adored (2026-06-10).** The placeholder name retired (#125) across display brand, technical identifiers, and living docs. History deliberately **not** rewritten (decision below / rename story).
8. **Phase 7 — Bulk upload → durable pool → grouped, numbered items (2026-06-13 → 06-14).** Metadata-first ordering **inverted**: dump images fast, group/name later or never. `items.name`/`photos.itemId` made nullable, per-collection catalog number added, **Blob client-upload** durable pool, gentle deferred-metadata surfacing. Adopted `adversarial-review` as a gate.
9. **Phase 8 — Real card images, covers, slugs, analytics (2026-06-14 → 06-16).** UI-fidelity + URL fixes: real hero/cover photos on cards; member-or-owner page IDOR fix (`purses-82r`); **short collection slugs** replaced raw ULIDs under "slug for nav, id for data" (#190). Playwright runs selectively on UI changes; analytics added.
10. **Phase 9 — Authz overhaul: close live cross-tenant holes (2026-06-17 → 06-18).** A security cluster closed verified live cross-tenant read/write/IDOR holes: shared `requireApiCollectionAccess` (#196), cross-curator triage scoped (#198), session/result URLs got numbers (#197), the whole `/api/sort-results` subtree guarded (#200), dead routes deleted (#201). The heavier DAL chokepoint was deliberately **deferred** to epic `purses-pv9` — security first, structure later.
11. **Phase 10 — "Sea Glass" theme refresh (2026-06-28).** The Luminous palette retuned without changing its bones. Light moved off pure white to a **cool sea-glass ground** (`#D3E2E5`; cards still rise to white); dark became **"Sea Glass at Night"** — one teal spine inverted toward black, raised planes lifted by an inset highlight + a luminous rim + a glow (*elevation by light, not a muddy mid-tone*). The spark went **citron → marigold** (`#EFCB77`), decor **mauve → soft violet** (`#B5AACC`, now used freely), and the dark primary **cornflower-blue → luminous teal** (`#4FB6C7`); new `content-deep` / `spark-soft` / `decor-soft` tokens; body type bumped to 17px and h1 to weight 700. `src/app/globals.css` is the source of truth; `DESIGN.md` updated to match.

### Decisions log

Each entry is **Decision / Rationale / Status**. Where design and shipped code diverged, that is stated explicitly.

**1. Blank-slate service-first refactor (Prisma → Drizzle, DecisionEvents immutable).**
- *Decision:* Wipe the source (`3342e84`) and rebuild as Services → Repositories → thin API handlers → React-calls-APIs; DecisionEvents append-only; scores/rankings lazily derived; ULID PKs.
- *Rationale:* Keeps the data model simple and authoritative and concentrates authorization server-side. The original Prisma stack and its onboarding/roles code were erased in one move rather than incrementally migrated.
- *Status:* **Shipped.** Layout verified: `src/server/{api,services,repositories,dal}`; `decision_events` in `schema.ts:203`.

**2. Auth: NextAuth v4 Credentials + magic-link; JWT sessions (design said DB). — SUPERSEDED by entry 26 (better-auth + DB sessions). Historical record only; none of it is the current architecture.**
- *Decision:* NextAuth v4 + `@auth/drizzle-adapter`; **Credentials** (email+password, bcrypt) as the primary sign-in plus an EmailProvider magic-link path. The canonical NextAuth schema (`user`/`account`/`session`/`verificationToken`) forced renaming the legacy `users` table; **users hard-delete** (no `deletedAt`), collections/items keep soft-delete.
- *Rationale / divergence:* The auth **design specified database-backed sessions and a `session` table the app does not use as a session store** — the shipped code **pivoted to JWT** (`src/lib/auth.ts:124` `strategy: "jwt"`). And **prod magic-link email was never wired**: `sendVerificationRequest` only `console.log`s in development (`src/lib/auth.ts:78-80`), so the magic-link is dev-only despite the provider being configured.
- *Status:* **RETIRED — superseded by entry 26.** NextAuth v4, the `DrizzleAdapter`, the JWT strategy, `src/lib/auth-callbacks.ts`, and the **bcrypt** credentials path no longer exist in the codebase (`bcryptjs`/`@types/bcryptjs` are no longer dependencies); Google is now the only supported product login, and sessions are DB rows. The display **name is still editable** via `PATCH /api/users/me` (name-only) and is fresh on the next request without a token-refresh dance, because `getSession` does a per-request DB read (no cookie-cache) — `purses-wew`.

**3. The `VERCEL=1`-in-`.env.local` `__Secure-` cookie gotcha.**
- *Decision:* Never let Vercel system vars (`VERCEL` / `VERCEL_ENV` / `VERCEL_URL` / `VERCEL_OIDC_TOKEN`) live in `.env.local`; neutralize `VERCEL` in the Playwright env block; **do NOT override `useSecureCookies`** (keep Vercel's native prod Secure detection).
- *Rationale:* `vercel env pull` wrote `VERCEL=1` into `.env.local`, which makes NextAuth emit a Secure-flagged `__Secure-next-auth.session-token` cookie that browsers **drop over `http://localhost`** → middleware's `getToken()` saw no session → every authenticated request bounced to `/login`. The bug was env hygiene, not auth code (incident #62, fix #64).
- *Status:* **Shipped + encoded as a startup guard.** `src/lib/env.ts:69-76` warns loudly when `VERCEL` is set and `AUTH_URL` is `http://` rather than overriding cookie behavior.

**4. Neon branch-per-environment.**
- *Decision:* `DATABASE_URL` scoped so **Production → `main` DB; all Previews + local dev → a long-lived `development` DB**. No per-PR ephemeral branches.
- *Rationale:* After a prod connection string leaked into `.env.local`, prod had to be unreachable from any non-production deploy. Per-PR branches were rejected as more machinery than needed — the simplest design that protects prod.
- *Status:* **Shipped** (topology lives in `docs/DEPLOYMENT.md` + the kept `neon-migration.md` history note).

**5. TONE.md first-order; Luminous design system accountable to it.**
- *Decision:* TONE.md is the **first-order, medium-agnostic** contract (constraints, never hexes/durations); DESIGN.md and copy answer to it; an exception is a written amendment to TONE. The Luminous Gallery delivers the feel; **"Brand never speaks Danger"** (red/amber/green reserved for ANSI Z535 safety meanings, never decorative); fourth tier **Release → Onward** ("Release"/"letting go" read clinical/grief-adjacent).
- *Rationale:* Two warm palettes were rejected as cozy-not-gallery; the durable fix was to make tone the contract and the visuals accountable to it. *"Restraint is not minimalism"* — Adored is aesthetic, not minimalist.
- *Status:* **Shipped (#82).** See `DESIGN.md`; tier tokens love/like/maybe/onward.

**6. Sort-ranking model: single [0,1] score, band-center seeding.**
- *Decision:* One continuous score in [0,1], computed in two order-independent passes. Triage seeds each item at its **tier-band center** (Love/Like/Maybe/Onward = **0.875 / 0.625 / 0.375 / 0.125**); pairwise refines with **asymmetric deltas (win +0.10, loss −0.05)** so rising is easier than falling (affirmation bias). Cross-tier override is emergent and symmetric (2 consistent wins promote, 3 losses demote); tie = no swing, skip = no-op.
- *Rationale:* The old edge-seeds read every tier one bucket too high (`seed→getBucket` was not an identity round-trip — `purses-7lh`), and a floored delta could never demote. Center-seeding makes `seed→getBucket` an identity round-trip and gives ±0.125 of pairwise headroom.
- *Status:* **Superseded by entry 24 (Epic 0).** The band-center **triage seed** survives (`ScoringService`'s `TIER_SEED`, still the item's `score`/bucket), but the **asymmetric pairwise deltas were retired** — pairwise no longer moves score; ordering within Love+Like is now a binary-insertion replay materialized as `order_rank`. `WIN_DELTA`/`LOSS_DELTA` no longer exist.

**7. Photo pool: upload-first, defer metadata; neon-http has no transactions.**
- *Decision:* Upload-first into a **durable per-collection pool** (`item_id IS NULL`), defer metadata, promote into grouped numbered items. Because **neon-http has no transactions**, the order is **create-item → assign-photos** (only partial failure = a harmless empty item), and assignment is a **single guarded `UPDATE … WHERE collection_id = c AND id IN ids AND item_id IS NULL AND deleted_at IS NULL`** whose **affected-row-count vs requested-count is the IDOR/double-assign guard**. **Hero is folded into the same UPDATE** (`is_hero = (id = heroPhotoId)`) so there is never a photos-but-no-hero window. Catalog number = `MAX(number)+1` with **retry-on-23505** (no txn to lock).
- *Rationale:* Getting photos in fast is the urgent real task; a stateless/transactionless driver means the WHERE clause and the count comparison *are* the integrity mechanism.
- *Status:* **Shipped.** `assignPooledPhotosToItem` + the explanatory comment at `src/server/repositories/implementations/PhotoRepository.ts:202-232` (returns count; caller compares); pre-check `countAvailablePooled` at `:240`; the `items_collection_number_unique` 23505 retry now goes through the shared `allocateWithRetry` primitive (see invariants above).

**8. Vercel Blob client-upload; `onUploadCompleted` can't reach localhost.**
- *Decision:* Bulk upload uses Blob **client-upload** (`@vercel/blob/client`) to bypass the 4.5 MB serverless body cap. The durable `photos` row is written **only** in the server `onUploadCompleted` callback, trusting the **signed `tokenPayload`** (never the client).
- *Rationale / divergence:* That callback **cannot reach `localhost`**, so the full path is verifiable **only on a Vercel preview deploy**, not local dev. The row-write was extracted into a pure `recordPooledPhoto` seam precisely so it is unit/DB-testable without Blob's network callback.
- *Status:* **Shipped** (pool/upload route + `recordPooledPhoto`).

**9. Reassign is one operation; hero reconciliation rules.**
- *Decision:* Move / split / return-to-pool are **one reassign**: set the selected photos' `item_id` (existing item = move, new item = split, `NULL` = return to pool). Hero rules: moved photos become non-hero on an existing target; the first moved photo is hero of a new item; the pool clears hero; a **source that loses its hero but keeps photos auto-promotes its first remaining photo**; **empty source items are left, not auto-deleted — for predictability**. `getNextCatalogNumber` maxes over **soft-deleted rows too** (a tombstoned number is never reused).
- *Rationale:* Treating the three gestures as one `item_id` reassignment is the smallest model; the deliberate "don't auto-delete empty sources" keeps behavior predictable rather than clever.
- *Status:* **Shipped.** `reassignPhotos` (`PhotoRepository.ts:259-284`, `targetItemId|null`); `getNextCatalogNumber` MAX-over-all-rows at `ItemRepository.ts:103-114`.

**10. URL model "slug for nav, id for data".**
- *Decision:* Collection page URLs use a human **slug**; session/result URLs use per-collection **sequential numbers**; **never raw ULIDs** in user-facing URLs. The slug/number resolves the entity **only at the page boundary**; every downstream DB query, image/file URL, client fetch prop, redirect, and integrity guard uses the immutable ULID.
- *Rationale:* **Slugs are globally unique (not per-owner)** *because* per-owner numbering would make a shared link resolve to a different collection for each viewer. A **reserved-slug blocklist** (e.g. `new`) exists *because* `/collections/new` is a static route Next resolves **before** the dynamic `[id]`. The **§7 audit rule**: every `params.id` downstream is wrong unless (a) passed to the access guard or (b) used as a nav href.
- *Status:* **Shipped** (#190 collections / #197 sessions+results). `RESERVED_COLLECTION_SLUGS = new Set(["new"])` at `src/lib/collections/slug.ts:7`.

**11. E2E testing strategy.**
- *Decision:* **Playwright over Cypress** (first-class multi-device emulation — iPad-landscape / iPhone-13 / desktop, WebKit ≈ iOS Safari). Test the **production build** (`next build && next start`), not `next dev`. Use an **ephemeral Docker Postgres** with a **hard guard that refuses any non-local host** (so it can never hit a Neon branch). **Mock the `@vercel/blob` boundary**; test auth with signed Better Auth session fixtures rather than OAuth round-trips.
- *Rationale:* The TRUNCATE in `resetDb()` must never touch a real DB — so the guard is a **fail-closed allowlist** (host ∈ {localhost, 127.0.0.1, ::1}), correct-by-construction rather than a denylist of three known Neon hosts.
- *Status:* **Shipped.** Guard in `e2e/fixtures/db.ts`; blob stubbed in `e2e/sort-images.spec.ts`. Middleware public paths (`api/auth|login|signup|shared-results|api/shared-results|tutorial|tutorials|onboarding|invitations|api/invitations/accept`) at `src/proxy.ts` (renamed from `middleware.ts`, decision 36; the dead `shared` exclusion became `shared-results` so anonymous share links render — the token is the capability). `invitations` (the `/invitations/[token]` accept page) and `api/invitations/accept` (its GET preview) are excluded for the same reason — an invite link must render for a signed-out recipient; `POST /api/invitations/accept` stays session-gated at the route (the matcher exclusion is method-agnostic, but it's only the UX redirect, never the security boundary). The login redirect carries `callbackUrl=pathname` so an emailed `/invitations/[token]` link survives the sign-in round-trip; better-auth's `trustedOrigins` check rejects non-relative callback URLs.
- *Worktree-derived ports (no more fixed `:5433`/`:3100`):* the project runs **parallel git worktrees**, and a fixed container name + port meant the second worktree's run either `docker rm -f`'d the first one's container or silently `TRUNCATE`d its database mid-run. `e2e/fixtures/test-db.sh` now derives a **slot** from a `cksum` hash of the worktree path (`0..499`) → container `pi-e2e-db-<slot>`, DB port `15432 + slot`, **and the Next app port `3100 + slot`** (the app port has to move with the DB port, or Playwright's `reuseExistingServer` hands worktree B the app worktree A already started against A's database). The script is the **single source of the URLs** — `test-db.sh url` / `app-url` / `name`; `e2e/fixtures/db.ts` shells out to it at import time and exports `TEST_DATABASE_URL`/`TEST_BASE_URL`, and `playwright.config.ts` reads those. Nothing re-derives a literal, and CI no longer pins `DATABASE_URL_TEST` in the e2e job (a literal there would point Playwright at a port nothing opened).

**18. Account deletion = purge owned data + scrub PII (pv9 PR6, `purses-hybm`).**
- *Decision:* `DELETE /api/users/me` is a real, irreversible erasure via `AccountDeletionService`, not a soft-delete. Phases: (1) purge **every** owned collection — active **and** soft-deleted (enumerated by `findByOwnerIncludingDeleted`) — by **reusing `CollectionPurgeService.purge`** per collection (canonical cascade + `collection.purge` audit + post-commit blob `del`; no drift); (2) delete the user's curator-private rows globally (`deleteByCurator`/`deleteByUser` — sessions/sort-results/+children/preferences/memberships) in one transaction; (3) **scrub, don't delete,** the user's account-linking identifiers on *retained shared content* in others' collections — `photos.uploaded_by` and accepted `invitations.email` → a per-id tombstone (deleting would destroy other owners' collection content); (4) scrub the `user` row PII + delete `account`/`session`/`verificationToken` in one transaction. **Fail-loud ordering:** if any owned-collection purge throws, abort **before** the borrowed pass and the PII scrub → route `500`, PII intact, **retryable** (the scrubs are idempotent match-by-identifier updates).

Shared content the user merely *contributed* to others' collections (photos/items) belongs to those owners, so it is de-identified, not deleted. The user row is **retained, scrubbed** (not row-deleted) to keep FK-less `audit_log.actorId` resolving to a tombstone rather than dangling.

**20. Item dispositions: curator-scoped triage shelving + the `disposed ⟺ untriaged` invariant (Epic C PR1).**
- *Decision:* A new **curator-scoped** `item_dispositions` table (migration `0008`) lets a curator park an *untriaged* item out of the sort queue without a verdict: `set_aside` (Not Mine) or `deferred` (Not Yet). - *Rationale:* Disposed items emit **no decision events**, so they are simply absent from derived preferences and results with **zero `ScoringService` change** — the append-only event log stays the single source of truth. Because the table has no cascade, dispositions are erased in **all three purge vectors**: item purge (`ItemPurgeService.deleteByItem`), collection purge (`CollectionPurgeService.deleteByCollection`), and account deletion (`AccountDeletionService.deleteByCurator`, the curator's borrowed-collection slice).

**21. Session lifecycle: pause/resume, set-aside undo (restore), and the `sessions_active_unique` 409 net (Epic C PR3).**
- *Decision:* A sort session's lifecycle is driven through three paths. **Pause/resume** is a plain `PATCH /api/sessions/[id] { status }` — `status: "paused"` ("Take a break") and `status: "active"` (Resume) — both members of the existing `UpdateSessionSchema` status enum (`active | paused | completed | abandoned`), so no new route. **Set aside** is the session `DELETE` (a soft-delete: `deletedAt` set), and its **undo** is a dedicated `POST /api/sessions/[id]/restore` rather than overloading `PATCH`/`DELETE` — necessary because the normal `GET·PATCH·DELETE` getters (`getSessionOrNull` → `findById`) **`404` on soft-deleted rows**, so restore resolves via `getSessionIncludingDeletedOrNull` → `findByIdIncludingDeleted` and then `restore` (clears `deletedAt`, sets `status: "active"`). Its authz mirrors `authorizeSession`'s order — existence (`404`) → collection gate (`requireApiCollectionAccess`) → **curator gate** (`curatorId !== userId` → `403`); that curator check is the only thing that closes the **purses-t9l** IDOR, because a *different* curator who is a member of the shared collection passes the collection gate. The **purses-4bhh interim mitigation**: the `sessions_active_unique` index is **unconditional** (spans active/paused/completed/soft-deleted), so a curator may hold only one session per collection. Two guards cover it — the sort landing **UI-gates** "New Session" whenever an active|paused session exists (offers Resume instead), **and** `createSession` catches the `sessions_active_unique` 23505 and throws `CurrentSessionExistsError`, which the shared `errorResponse` maps to a gentle **`409`** for *all* paths — **never a `500`** (the prior raw behavior). The calm "paused" `Badge` was re-mapped off the amber warning hue to a cool-blue benign token (`accent-cornflower`), matching the "Not yet / patient waiting" treatment.
- *Rationale:* Pause and set-aside are **calm, reversible, non-error** states — they must not borrow safety hues (DESIGN.md "Brand never speaks Danger"), hence the cornflower badge. Reusing `PATCH {status}` for pause/resume is the smallest model (the enum already existed); restore needs its own route only because soft-deleted rows are invisible to the standard getters, and a separate verb keeps the "undo" intent explicit. The 23505→409 net is a **belt-and-suspenders** companion to the UI gate: the gate prevents the common case, the catch makes the race/direct-API case gentle instead of a 500. This is deliberately an **interim** fix — the root redesign (a *partial* `sessions_active_unique` index that excludes terminal/soft-deleted rows, plus the matching guard) stays open in **purses-4bhh**.
- *Status:* **Shipped (Epic C PR3); the interim-mitigation half SUPERSEDED by entry 22.** Restore route `src/app/api/sessions/[id]/restore/route.ts` + `restoreSession`/`getSessionIncludingDeletedOrNull` on `SessionController`; `restore`/`findByIdIncludingDeleted` + the `isCurrentSessionConflict` 23505 catch → `CurrentSessionExistsError` in `SessionRepository.ts`; `errorResponse` 409 mapping (`src/server/api/http-errors.ts`); landing UI-gate + `ResumeControl` (`src/app/collections/[id]/sort/page.tsx`); paused `Badge` token (`src/components/ui/Badge.tsx`); e2e `e2e/sort-session.spec.ts` (pause + set-aside undo across viewports). **22. Session-uniqueness redesign: `sessions_active_unique` becomes a PARTIAL index — one IN-PROGRESS session per slot (Epic C, purses-4bhh/ydeu, migration 0009). Supersedes entry 21's interim mitigation.**
- *Decision:* Migration `0009` replaces the unconditional `UNIQUE(collection_id, curator_id)` with a **PARTIAL unique index** (`WHERE deleted_at IS NULL AND status IN ('active','paused')`), so the database enforces only **one IN-PROGRESS session per `(collection, curator)` slot**. Terminal (`completed`/`abandoned`) and soft-deleted (`set_aside`) rows **fall out of the predicate and free the slot** — a curator can start a new sort after completing, abandoning, or setting aside the previous one. The cap changes from *"one session per slot ever"* to *"unbounded historical rows, one in-progress"* (auth-gated, owner/curator only). **Predicate↔guard invariant — all three writers that move a row INTO the partial predicate catch the `23505` → `CurrentSessionExistsError` → `409` (never a `500`):** (1) `create()` (a fresh `active` row into an occupied slot), (2) `restore()` (undo set-aside re-enters as `active` while a newer in-progress session holds the slot), and (3) `update()` (a `PATCH {status}` terminal→`active`/`paused` transition re-entering the predicate). `restoreSession` adds a friendly pre-check (`findInProgress` widens `findActive` to `status IN (active,paused)`) that returns the `409` BEFORE the UPDATE; the repo's `restore()`/`update()`/`create()` catches are the race backstops. **Serialization gotcha:** drizzle-kit 0.20.17 (snapshot v5) cannot serialize a partial-index predicate, so `0009` is **hand-authored**; `schema.ts` carries the `.where()` only to record the intended truth (the generated snapshot can't encode it — `db:generate` emits nothing for this change, so the SQL is the source of truth). The migration is **forward-only** (no safe down — recreating the unconditional index would `23505` once >1 terminal/soft-deleted row per slot exists). The defense-in-depth UI gate + 23505→409 net from entry 21 are kept.
- *Rationale:* Entry 21's unconditional index over-constrained the model — it forbade a curator from *ever* starting a second sort of a collection, even after the first was completed or set aside, which is the normal flow (purses-4bhh root fix). A partial index expresses the real invariant ("one live sort at a time") in the database itself, where it can't be bypassed. The three-writer catch is the **predicate↔guard contract**: every code path that could push a second row into the predicate must translate the unique violation into the same gentle, typed `409`, so a race or direct-API call is never a raw `500`. The pre-check makes the common case (you set this aside, then started a new sort, then hit undo) decline gently — the set-aside session stays set aside — without relying on the DB error alone.
- *Status:* **Shipped (Epic C).** Migration `drizzle/0009_partial_active_session.sql`; the `activeIdx` `.where()` in `src/lib/db/schema.ts`; `create`/`restore`/`update` 23505 catches + `findInProgress` + `isCurrentSessionConflict` in `src/server/repositories/implementations/SessionRepository.ts`; `restoreSession` pre-check in `src/server/api/sessions.ts`; `errorResponse` 409 mapping (`src/server/api/http-errors.ts`). The CI job is renamed `Recompute bench (p95 gate)`, its `continue-on-error` is dropped, and `scripts/bench-recompute.ts` now **exits 1** on a regression, on a **missing baseline**, and on an unexpected error (a gate that cannot run is not a pass). It still runs only when the `hot` paths-filter fires, and when skipped GitHub reports success — so it is safe to mark required.
- *Rationale:* The job was theater: `continue-on-error` **and** a script that could never fail (a `.finally(() => process.exit(0))`) meant a genuine O(N²) regression would have gone green. The **4× threshold is deliberately generous, not lazy**: a GitHub runner already measures ~1.5× the committed dev-Mac baseline from hardware alone, so a 2× gate would flake — and a flaky gate gets disabled, which is worse than no gate. 4× still catches the only thing this bench exists for (an O(N²) path returning is a multiple-x blowup at N=100, not a 3× one). It is a **shape** gate, not an absolute-latency gate — local Docker p95 ≠ Neon p95.
- *Status:* **Shipped.** `bench` job in `.github/workflows/ci.yml`; `benchVerdict` + the fail/warn multipliers in `scripts/bench-recompute.ts` (+ `scripts/bench-recompute.test.ts`); baseline at `bench/recompute-baseline.json` (re-baseline **deliberately**, with `--update-baseline`, only on an intended algorithm change).

**32. Preview deploys trust their own branch alias — derived, never wildcarded (`purses-bmpy`, 2026-07-11).**
- *Decision:* `previewTrustedOrigins()` (`src/lib/env.ts`) feeds better-auth's `trustedOrigins`. It returns `[]` unless `VERCEL_ENV === "preview"`; on preview it returns this deployment's own Vercel-injected hostnames (`VERCEL_URL`, `VERCEL_BRANCH_URL`). Hosts containing `*` or `?` are dropped.
- *Rationale:* `AUTH_URL` is unset in the Preview environment, so `env.ts` falls back to `https://${VERCEL_URL}` — the per-deploy hostname — and better-auth's `getTrustedOrigins()` trusts *exactly* `[new URL(baseURL).origin]` (it does **not** fall back to the request host). But every preview is also aliased at the branch URL, which is what Vercel's PR comment links to, so `Origin` ≠ `baseURL` and sign-in returned `403 INVALID_ORIGIN` on the one URL a reviewer actually clicks. Verified live: the same POST to the deployment URL reached the credential check (`401`), and to the branch alias did not (`403`). Fail-closed, not a leak — nothing was over-trusted. **Never wildcard this list:** better-auth's `matchesOriginPattern()` treats `*`/`?` as wildcards, and the same list also gates `callbackURL`/`redirectTo`, so `*.vercel.app` would trust every Vercel deployment on the internet — including an attacker's — and hand them a redirect target. `BETTER_AUTH_TRUSTED_ORIGINS` (a static env list) was deliberately *not* used: it cannot express "this deploy's alias", and it would move the security decision into the Vercel dashboard where no code review sees it.
- *Status:* **Shipped.** Production's trusted set is unchanged (`VERCEL_ENV="production"` short-circuits to `[]`); two tests pin that a preview origin can never leak into production.

**33. Drizzle 0.45 + one squashed baseline; `drizzle/` history lives in git, not on disk (`purses-c3je`, 2026-07-12).**
- *Decision:* `drizzle-orm` 0.30.10 → ^0.45.2 and `drizzle-kit` 0.20.17 → ^0.31 (moved to **devDependencies** — it is a codegen CLI; the runtime migrator imports from `drizzle-orm`). `legacy-peer-deps=true` is **gone** from `.npmrc` (the file is deleted): the exact drizzle pins were the only thing forcing it, and that flag had been suppressing peer resolution for the *whole tree*. `drizzle/`'s **17 migrations are squashed to a single generated `0000_init`** (journal v7). Migration numbers `0000`–`0016` referenced elsewhere in this doc **no longer exist as files** — that history is in git, and the applied schema is unchanged.
- *Rationale:* All DB data was declared disposable (owner, 2026-07-12), which retires the reason to carry the history: the alternative (`drizzle-kit up`, translating 17 v5 snapshots to v7 while preserving every `when` byte-identically) is a fiddly dance whose only purpose is protecting data we don't keep. Squashing sidesteps the translation entirely — the new kit writes its own format natively. **Verified, not assumed:** a DB built from the old 17 vs. one built from the new baseline matched on **45/45 constraints, 32/32 indexes, and an identical column set** (name+type+default+nullability), with all three partial-index predicates byte-identical. Physical column *order* differs (an `ALTER TABLE ADD COLUMN` appends; a fresh baseline uses declaration order) and is inert — drizzle names every column explicitly and never `SELECT *`s.
- *The trap this closes:* the migrator's already-applied test (`drizzle-orm/pg-core/dialect.js:56`) compares **only** the journal `when` timestamp against the newest applied row; the SHA-256 `hash` is written and **never read back**. So a re-baselined `drizzle/` replays the whole schema history on the next deploy — and `vercel-build` runs `db:migrate` on *every* deploy. With disposable data that is a failed deploy, not data loss; with real data it would be a catastrophe. Guard filed as `purses-mebk.1` (pin migration content hashes) — **do it before the first real user.**
- *Two facts `schema.ts` was hiding, both surfaced by the squash:* (1) `memberships_role_check` (decision 17's `CHECK (role IN ('owner','curator'))`) existed **only in migration SQL** — drizzle-orm 0.30 had no `check()` API — so `schema.ts` was a **lossy** view of the applied schema and a naive regeneration would have shipped `role` as free text. It is now declared via `check()`. (2) `invitations.token` was declared unique **twice under the same name** (a column `.unique()` *and* an explicit `uniqueIndex`); drizzle-kit 0.20 emitted `CREATE UNIQUE INDEX IF NOT EXISTS`, so the duplicate silently no-op'd — 0.31 drops the `IF NOT EXISTS` and it is a fatal `42P07`. The dead index is removed; the redundant (differently-named) twin on `sort_result_shares.share_token` is removed too.
- *Errors are now WRAPPED — this changed behavior:* drizzle 0.45 throws a plain `Error` (`"Failed query: …"`) with the real `PostgresError` demoted to **`.cause`**. Every conflict detector read `error.code` at the top level, so all five silently returned `false`: a session-slot collision stopped mapping to a gentle **409** and became a **500**, and two MAX+1 allocation retries stopped retrying. One shared `isUniqueViolation(error, constraint)` (`src/server/repositories/pg-conflict.ts`) now walks the cause chain and matches `constraint_name` exactly. Anything that inspects a Postgres error **must** unwrap `.cause` (`src/lib/db-error-log.ts` already did — that is why the *logging* path was correct while the *acting* paths were not).
- *Dependency resolution moved inside the auth stack:* without the flag, `better-call` nests under `better-auth` with its own **zod 4**, while app code keeps **zod 3**. The flag had been feeding `better-call` a zod major it declares incompatible — so dropping it fixed a latent wrong rather than introducing one.
- *`db:reset` (`scripts/db-reset.ts`):* the declarative, committed way to re-derive a database from `schema.ts`. It drops **both** `public` **and** `drizzle` — the migrator's ledger is `drizzle.__drizzle_migrations`, so dropping only `public` leaves it alive and the *next* reset applies nothing, prints success, and hands you an **empty database with a green light**. Fail-closed: refuses an ambient `DATABASE_URL` (dotenv does not override an already-set var, so a stray export would silently beat `.env.local` — with a `DROP` payload), refuses a **non-TTY stdin** (an echo-back prompt alone is not a lock: `echo "host/db" | npm run db:reset` satisfies it, which is exactly what a CI job or an agent does when a prompt looks hung), and makes you type the target host back. No `--force`: a flag is re-runnable from shell history against the wrong database.
- *Also removed:* `db:backfill-numbers` (script, module, test, and its `vercel-build` step; `vercel-build` is now `db:migrate && next build`). It only healed rows `WHERE number IS NULL`, but `SessionRepository`/`SortResultRepository` allocate `number` at INSERT — so on any DB built from now on that state is unreachable. It was a one-shot legacy heal that had been a no-op on every deploy since. (`number` is still *nullable*: `purses-mebk.2`.)
- *Status:* **Shipped.**

**34. Async route params landed on Next 14, atomically with a falsifiable test oracle (`purses-9oxh.3`, 2026-07-12).**
- *Decision:* All **42** dynamic API route handlers moved to Next-15-style `{ params }: { params: Promise<{…}> }` + `const {…} = await params` **while still on Next 14**, in the same PR that flipped all **39 route-invoking test files** (~354 call sites) to pass `Promise.resolve(params)`. Next 14 passes a plain object at runtime and `await` resolves it to itself, so the migration is behavior-neutral now and mandatory-correct on Next 16.
- *Rationale:* the two halves are one atomic change — tests-only would 404 every route (sync `params.id` reads a Promise); routes-only leaves an oracle that cannot fail (`await plainObject` no-ops). Together, a mis-migrated handler 404s where an owner-2xx test asserts success. **Falsifiability was demonstrated, not argued:** a deliberately-reverted handler turned the DB tier red (6 tests, 2 files), then was restored byte-identical. The authz enumeration suite changed by exactly 3 lines (invocation + `importHandler` type); its allowlist, case keys, floors, and 403/404 predicate are byte-identical to before — verified by sorted-key-set diff. The 12 `page.test.tsx` files and the page enumeration oracle migrate with the pages in the Next 16 PR (`purses-9oxh.4`).
- *Status:* **Shipped.**

**35. Supply-chain hygiene: quarantine window + lockfile scanning (owner-approved 2026-07-12).**

**40. The DB enforces what the code already guaranteed; `any` removed from the mapper boundary (`purses-mebk.2` + `purses-22rp`, 2026-07-13).**
- *Decision:* `sessions.number`, `sort_results.number` and `photos.is_hero` are now **NOT NULL** (migrations `0001`, `0002` — the first additions on top of decision 33's squashed `0000_init` baseline). Every repository mapper under `src/server/repositories/implementations/` takes **`typeof <table>.$inferSelect`** instead of `row: any`.
- *Rationale — the two are one finding, not two:* all three columns were already unreachable-as-NULL (numbers are allocated at INSERT; every `is_hero` write sends an explicit boolean), so the DB was merely failing to say so. `photos.is_hero` was found **by** removing the `any`: the row type was `boolean | null` while `Photo.isHero` promised `boolean`, and `any` at the DB boundary had been laundering that mismatch silently — defeating precisely the guarantee the NOT NULL work exists to buy. Removing it also surfaced a **numeric/string write mismatch** (drizzle reads *and writes* `numeric` columns as `string`, while the domain carries `number`), dead `?? null` coalesces on columns that were never nullable, and union narrowings the `any` had been supplying invisibly. The boundary now **provably bites**: flipping a domain field's nullability fails `npm run build`, where it used to compile in silence.
- *Doing it now was the whole point:* the database is empty, so `SET NOT NULL` is a metadata-only ALTER over zero rows — no backfill, no expand/contract dance. That cheapness is a property of *now*, which is why the bead existed.
- *Guard added (`purses-mebk.1`):* `scripts/migration-hashes.test.ts` pins the SHA-256 of every committed migration. drizzle's migrator compares only the journal `when` timestamp and **never reads the recorded hash back** (decision 33's trap), so an edited or re-baselined migration replays silently — green CI, red prod deploy. Mutation-proven: one changed byte reds the test.
- *Status:* **Shipped.**
